🛡️ El CIA Triad: Los 3 Pilares de la Seguridad

Los 3 pilares fundamentales de INFORMACIÓN SEGURA

🔒

Confidentiality

"Nadie más puede ver esto"

Qué es: Solo gente autorizada accede a datos

Métodos: Encriptación, control de acceso

Ejemplo: Tus contraseñas, números de tarjeta

Amenaza: Hacking, phishing, insider threats

✓

Integrity

"Nadie puede cambiar esto"

Qué es: Datos no modificados por personas no autorizadas

Métodos: Firmas digitales, checksums, auditorías

Ejemplo: Transacciones bancarias, registros médicos

Amenaza: Inyecciones SQL, man-in-the-middle

⚡

Availability

"Esto está disponible cuando lo necesito"

Qué es: Servicios funcionan 24/7 confiablemente

Métodos: Redundancia, backups, mantenimiento

Ejemplo: Servicios en la nube, aplicaciones críticas

Amenaza: DDoS, fallos de hardware, sabotaje

⚖️ El Balance es la Clave

Los 3 pilares deben trabajar juntos. No sirve tener datos encriptados (confidencialidad) si el sistema está caído (disponibilidad) o los datos fueron modificados (integridad).

🔴 OWASP Top 10 2025: Las Amenazas Más Críticas

Los riesgos MÁS COMUNES encontrados en software 2025

🔴 TOP 3: El Triángulo del Riesgo

A01: Broken Access Control (Control de Acceso Roto)

Qué es: "El usuario A ve datos del usuario B"

Ejemplos: Privilege escalation, CORS misconfiguration

Impacto: Afecta 100% de apps testeadas

Prevención: Deny by default, server-side checks

A02: Security Misconfiguration (Configuración Insegura)

Qué es: "Dejamos las puertas sin cerrar"

Ejemplos: Cuentas default, servicios innecesarios, headers faltantes

Impacto: Afecta 90% de apps

Prevención: Hardening, configuración as code

A03: Software Supply Chain Failures (Fallas en Dependencias)

Qué es: "El malware viene de nuestras librerías"

Ejemplos: Vulnerabilidades en npm, pip, Maven packages

Impacto: Afecta cadena completa de distribución

Prevención: SBOM, verificación de componentes

⚠️ Otros Críticos

A04: Cryptographic Failures

Criptografía débil

A05: Injection

SQL injection, command injection

A07: Authentication Failures

Credenciales débiles

🔄 Integrando Seguridad en Cada Fase del SDLC

📋 PLANIFICACIÓN

  • Definir requisitos de seguridad
  • Análisis de riesgos inicial
  • Clasificación de datos
  • Planes de cumplimiento (GDPR, HIPAA)

🎨 DISEÑO

  • Threat modeling (¿Dónde pueden atacar?)
  • Arquitectura segura
  • Patrones de seguridad
  • Diseño de autenticación/autorización

💻 DESARROLLO

  • Codificación segura
  • Validación de entrada
  • Manejo de errores seguro
  • Gestión de secretos (API keys, contraseñas)

🧪 TESTING

  • SAST (Static Application Security Testing)
  • DAST (Dynamic Application Security Testing)
  • Pruebas de penetración
  • Testing de configuración

🚀 DEPLOYMENT

  • Hardening de infraestructura
  • Verificación de parches
  • Monitoreo de seguridad
  • Incident response plan

🔧 MANTENIMIENTO

  • Monitoreo continuo de vulnerabilidades
  • Parches de seguridad ágil
  • Auditorías regulares
  • Update de dependencias

🎯 La Clave: "Shift-Left"

Mover la seguridad hacia la izquierda (fases tempranas) del ciclo de desarrollo. Cuanto antes detectes problemas, más barato es arreglarlos.

📚 Casos Reales: Éxito y Fracaso en SSDLC

✅ CASO DE ÉXITO: Microsoft SDL

Contexto: Microsoft implementó SSDLC (Security Development Lifecycle) hace 20+ años

Filosofía: "Security Development Lifecycle by default" - seguridad en cada paso

Resultado: Windows 10/11 mucho más seguro que antecesores (Windows XP tenía vulnerabilidades masivas)

Beneficio: Confianza de usuarios, menos vulnerabilidades críticas, mejor reputación

💡 Lección: La inversión en seguridad PAGA a largo plazo

❌ CASO DE FRACASO: Log4j (2021)

Contexto: Popular librería de logging en Java, usada por millones

Problema: Vulnerabilidad crítica (Log4Shell) explotada masivamente en diciembre 2021

Afectó: Millones de aplicaciones globalmente (desde Apple hasta Tesla)

Causa: Falta de testing de seguridad en componente crítico

Impacto: Parches de emergencia globales, downtime masivo, millones perdidos

💡 Lección: Las dependencias son un riesgo crítico que debe monitorearse

🎯 La Diferencia

Microsoft invirtió en SSDLC desde el inicio. Log4j no tuvo recursos para auditorías de seguridad. Ambos casos muestran que la seguridad debe ser prioritaria, no opcional.

⭐ 5 Principios Clave para Recordar

1️⃣ Seguridad desde el INICIO

No es addon, es fundamento. "Shift-left" significa mover seguridad a las fases tempranas del desarrollo.

Detectar un bug en diseño cuesta $100. En producción cuesta $10,000.

2️⃣ Automática > Manual

Automatizar pruebas de seguridad en CI/CD pipeline. Menos errores humanos, feedback rápido.

Las herramientas trabajan 24/7 sin cansarse.

3️⃣ Educación Continua

Los desarrolladores son primera línea de defensa. Training regular sobre top 10 vulnerabilidades.

Un equipo educado es tu mejor firewall.

4️⃣ Colaboración

Dev + Security + Ops = Equipo de seguridad. No "ellos vs nosotros". Objetivo común: software seguro.

La seguridad es responsabilidad de todos.

5️⃣ Monitoreo y Respuesta

Incluso SSDLC bien hecho tiene vulnerabilidades. Monitoreo en producción es crítico. Incident response rápido.

La pregunta no es "si" seremos atacados, sino "cuándo".
